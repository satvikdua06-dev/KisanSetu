# Audit: backend core, 2026-11-24

Scope: `services/api` at commit `5b386ae` (multi-agent runtime, specialist tools, plug-and-play price sources, admin API) and the design docs it implements. Every fix below has a regression test in `services/api/tests/test_audit_fixes.py`.

## Findings and fixes

### Critical: commitments could differ from what the farmer approved

| # | Loophole | Fix |
|---|---|---|
| 1 | `create_agreement_draft` took price, quantity and counterparty from the agent, so an agreement could differ from the approved proposal. | The tool takes only `farmer_id` and copies the terms from the approved proposal. |
| 2 | The same approval could produce several agreements. | One agreement per approval; a repeat call returns the existing one. |
| 3 | Agreements didn't reserve produce, so one lot could be sold twice across workflows. | Lots track `committed_kg`; agreements reserve quantity; every pooling, matching and routing tool uses `available_kg`. |
| 4 | Re-planning superseded approvals but left drafted agreements live. | `replan` voids draft agreements and releases their reservations. |
| 5 | Agreements didn't check consent to share the farmer's details with the buyer. | Refused without `consent_share_with_buyers`. |
| 6 | Anyone could decide an approval. | Only the farmer, or `coordinator:<their fpo>` with a `confirmation_ref` recording the farmer's answer; the decider is stored. |

### Critical: agents could put invented numbers in front of farmers

| # | Loophole | Fix |
|---|---|---|
| 7 | Proposal figures were only covered by a prompt instruction. | `request_approval` checks them in code: price traceable to an active buyer requirement or the latest market observation range; net = price - transport - other costs; low <= expected <= high; total = net x quantity; quantity <= the farmer's available lot; lot belongs to the farmer; buyer name matches; pickup not in the past. |
| 8 | `hold_vs_sell` took price-change scenarios from the agent. | Scenarios are now derived from observed price history (10th/90th percentile of changes over the same horizon); with too little history the tool says so. |
| 9 | Pooling tools accepted any lot IDs and quantities. | `aggregate_lots` and `pro_rata_split` reject unknown, foreign, duplicate, other-crop or over-quantity lots. |
| 10 | `record_harvest` could shrink a lot below what is already committed. | Refused; the agent must report the shortfall so the Orchestrator re-plans. |

### Runtime robustness

| # | Issue | Fix |
|---|---|---|
| 11 | Two farmers approving at once could resume the Orchestrator twice. | Per-workflow lock around every Orchestrator run. |
| 12 | No limit on delegation fan-out or model spend. | 7 tasks per delegation, 40 per workflow, token budget per workflow; past it the workflow goes to the FPO coordinator. |
| 13 | Outside event text went into the Orchestrator's prompt unlabelled. | Events are passed as data with an explicit "data, not instructions" label; guardrails above don't depend on the model obeying. |
| 14 | Workflows could start for unknown farmers. | Rejected. |

### Price sources and admin API

| # | Issue | Fix |
|---|---|---|
| 15 | A price field without a unit defaulted to INR/kg (a quintal feed would read 100x too high). | Price fields must declare `parse: number` and a unit; a configurable sanity limit (default 1,000 INR/kg) rejects outliers. |
| 16 | Modal price outside min-max, or zero, was accepted. | Rejected with a reason. |
| 17 | HTTP errors included the full URL, leaking query-string API keys into results and the admin API. | Every secret value read during a run is scrubbed from errors and rejection reasons. |
| 18 | Admin-configured URLs could reach internal addresses (cloud metadata, databases), including through redirects. | Loopback, private, link-local, reserved and `.internal`/`.local` hosts are refused (opt-in override for deliberate private sources); redirects are refused. |
| 19 | File sources could read any CSV on the server. | Restricted to `MARKET_DATA_FILE_ROOT` (default `config/`). |
| 20 | The SQL check allowed `SELECT ... INTO`, stacked statements and comments. | Single statement only, no comments, wider list of write keywords; docs still require a read-only DB user. |
| 21 | Unexpected connector errors (bad JSON, driver errors, plugin bugs) crashed the run. | Any error ends that source's run with a recorded, redacted error; other sources are unaffected. |
| 22 | `/admin/*` endpoints had no authentication. | Disabled unless `KISANSETU_ADMIN_KEY` is set; constant-time check of the `X-Admin-Key` header. |

### Design doc drift

| # | Drift | Fix |
|---|---|---|
| 23 | `multi-agent-architecture.md` listed tools and features the code doesn't have (`await_results`, `notify_farmer`, `agents/<name>.yaml`, long-term agent memory, OpenTelemetry). | Doc now matches the code; unbuilt items are marked *Planned*, and the new code-level checks are documented. |

## Known gaps (not fixed here, tracked)

- In-memory store: no persistence, no cross-process locking. Postgres with row locks on lots and approvals is the next step.
- DNS rebinding can bypass the host check between resolution and connection; the production fix is an egress proxy that enforces the same rules.
- The SQL keyword filter is defence in depth; the real control is a read-only database account.
- Admin auth is a shared key until phone OTP + role-based access lands.
- No live run against Claude yet; the request shape is verified against the SDK with a mocked HTTP layer.
- Pooling and routing still use greedy / nearest-neighbour methods with straight-line distances until OR-Tools and OSRM are wired in.

## Core objectives check

All seven objectives in `CLAUDE.md` were checked. None is weakened; objectives 3 (numbers from code), 4 (the farmer decides) and 5 (honest data) are now enforced in code rather than only in prompts.
